# 平台功能与 UI 自动化测试分离方案

> 版本：1.0
> 日期：2026-09-21
> 状态：方案讨论稿
> 关联：`docs/dev-test-environment-plan.md`（本机环境治理）、`docs/agent-evaluation-plan.md`（Agent 评测）

## 一、背景与问题

本机调整为开发、测试环境后，需要回答：**能否在无账号登录的情况下进行全面测试？**

评估结论：可以分两半看——

- **平台功能测试可以做到零账号**（协议、引擎、自动化、适配、DB、前端），工程现状已基本具备。
- **闲鱼 UI 自动化整体回归做不到零账号**，需要测试小号 + 大号配合。

核心衔接资产：**主号数据的脱敏快照**（已确认采用脱敏快照方案，去 Cookie/Token/买家 ID，仅作回放与种子）。

## 二、分离架构

```
┌─────────────────────────────────────────────┐
│            测试数据 / 夹具层                    │
│  脱敏种子 · golden 回放 · 本地替身 · 模型桩     │
└───────────────┬───────────────┬─────────────┘
                │               │
┌───────────────▼───────┐ ┌─────▼─────────────────┐
│   平台功能测试          │ │  闲鱼 UI 自动化回归     │
│   server · engine ·    │ │  internal/browser     │
│   automation · adapter │ │  真实页面：登录/滑块/   │
│   · db · xianyu 协议    │ │  订单/发卡/WS          │
│   ─── 无需账号          │ │   ─── 需测试小号+大号   │
└───────────────┬───────┘ └─────┬─────────────────┘
                │               │
        ┌───────▼───────────────▼───────┐
        │   Agent 评测 → 卡口门禁          │
        │   意图/负向/回复指标 · 调优闭环    │
        └───────────────────────────────┘
```

## 三、平台功能测试（零账号，现状已基本具备）

| 层 | 数据源 | 现状 |
|---|---|---|
| 协议层 `internal/xianyu/protocol` | golden 录制（真实抓包样本锁定签名/解密） | 已有 `golden_test.go` |
| MTOP/WS 层 `internal/xianyu/mtop`、`ws` | httptest 本地替身 + 录制响应回放 | 已有，覆盖发送/回显/凭证轮换 |
| 引擎/自动化/适配 `internal/engine` 等 | 注入替身 + 内存数据库 + mock OpenAI server | 已有（`ai_scope_test.go` 等） |
| DB 层 `internal/db` | SQLite 内存库 + 三方言功能栈 | 已有 `TestMultiDB_*` |
| 前端 | vitest + tsc | 已有 |

覆盖率现状佐证（均无真实账号）：Go 全库 81.4%、前端 79%。核心链路包级覆盖为 automation 88.5%、engine 89.3%、xianyu/ws 88.8%、adapter 83.7%、db 82.1%；部分核心文件未达 100% 门槛（如 manual_delivery、automation_delivery_proof、adapter_events），明细见 `docs/architecture/core-chain-coverage.md`。

## 四、UI 自动化整体回归（需要测试小号 + 大号）

必要性：`internal/browser` 的真实页面操作依赖真实闲鱼页面结构，mock 页面无法替代；冻结滑块规范也要求选择器行为不变。

- **测试小号**：跑低风险链路——页面可达性、渲染、滑块出没、登录流程。
- **测试大号**：跑关键业务回归——订单、发卡、WS、确认发货。
- 执行方式：独立回归脚本 + 独立开关，**不进默认门禁**，避免本机开发每次都被真实平台拖住。工程已有浏览器集成开关 `RUN_BROWSER_INTEGRATION`（见 `docker-compose.functional.yml` 的 `browser-integration-test`，真浏览器 + 本地页面），UI 自动化整体回归应在此基础上扩展真实平台页面路径；`TEST_XIANYU_LIVE` 只用于需要真实账号的真实平台协议调用，两者职责不同，不混用。

## 五、脱敏快照方案（已确认采用）

原则：**主号数据在测试环境「存在性可用、凭证不可用」**。

| 项 | 处理 |
|---|---|
| 订单、商品、会话、聊天记录 | 保留形状与分布，供回放与评测 |
| Cookie、Token | 删除，绝不进入本机测试环境 |
| 买家/卖家真实 ID | 脱敏为 fixture ID |
| 卡密等敏感内容 | 不复制（沿用 `dbseed` 现有脱敏逻辑） |

落地方式：
- 主号数据在部署机上（或一次性生成时）产出脱敏快照；
- 快照入库为本机测试种子 + 回放样本 + Agent 评测集；
- 生成后主号数据从本机运行路径移除，本机只持有脱敏快照。

## 六、评测衔接

- 平台功能测试沉淀的脱敏快照 / 真实 IM 会话 → 直接作为 Agent 评测集来源（见 Agent 评测方案）。
- UI 自动化回归中的真实会话数据，同样可脱敏后回流到回放样本库。

## 七、落地顺序建议

1. 本机环境治理落地（见环境治理方案）。
2. 建立脱敏快照生成工具（可基于 `cmd/dbseed` 扩展）。
3. 平台功能测试补强：扩充 golden 录制覆盖面（WS 帧、MTOP 响应变体）。
4. UI 自动化回归脚本 + 测试小号/大号准备。
5. Agent 评测机制建设（见评测方案）。
