# 流量回放式评测机制 · 可行性评估

> 日期：2026-10-11
> 状态：评估结论 + 落地建议（未实施）
> 关联：`docs/agent-evaluation-plan.md`（评测机制方案 v1.0）、`docs/customer-service-agent-upgrade-plan.md`（Agent 升级计划）、`docs/test-separation-plan.md`（测试分离方案）、`docs/slider-captcha-frozen-spec.md`（滑块冻结规范）

## 一、结论

设想（生产缺陷筛选沉淀 → 每次开发后流量回放评测）**技术上可行**，但**不可按「全自动流量回放」设计**。建议形态：

> **缺陷样本库 + 分层离线回放评测**

三个前提必须先解决，否则产出的是一组没人信的数字：

| 前提 | 现状 | 判断 |
| --- | --- | --- |
| 标签质量：怎么知道「失误」 | 发货失败有结构化信号；客服语义失误没有 | **最大瓶颈**，不可全自动 |
| 回放密封性：不能走真实平台 | 滑块验证码已生产冻结、平台有风控 | 必须离线沙箱 |
| 样本库治理：只增不减会腐化 | 无 | 需分层 + 生命周期 |

可行性总评（按数据源）：

| 数据源 | 可行性 | 关键依据 |
| --- | --- | --- |
| 自动发货出错 | **高** | `automation_runs` 已有 `status`（success/failed/needs_review）+ `error_message` + `NoRetryErrorPrefix` |
| 客服技术性失败 | **中高** | 回落与预算耗尽在代码里可观测，但当前只写日志、未结构化落库 |
| 客服语义失误 | **中低** | 系统无法自知答错，且项目**没有「转人工」信号**，缺最天然的负标签 |
| 离线回放执行 | **高** | 已有 `AIGenerator` 接缝 + mock OpenAI server 范式 + `ai_conversations` 落库 |
| 运行时重放真实链路 | **否决** | 滑块验证码生产冻结（AGENTS.md §1.8），平台风控与账号成本不可接受 |
| 纳入门禁 | **分层可行** | 决策层可进默认门禁；LLM 层只进发版门禁 |

## 三、数据源可行性分档

### 3.1 三档差异

| 档位 | 数据源 | 可自动采集 | 说明 |
| --- | --- | --- | --- |
| A | 自动发货出错 | 完全可自动 | `status=failed/needs_review` 是确定性错误码；`NoRetryErrorPrefix` 还区分永久失败与可重试 |
| B | 客服技术性失败 | 需补埋点 | 回落（预算耗尽 / 模型异常 / 工具故障）可观测，但只写 `slog`，无结构化记录 |
| C | 客服语义失误 | 不可自动 | 系统无自知能力，无人工接管信号 |

### 3.2 结构性阻碍：失败现场易失

**这是必须先解决的第一件事。**

`automation_runs` 是**可变当前态表**，不是 append-only 事件流：

- 写入是 `INSERT IGNORE` + 大量 `UPDATE`（`internal/db/automation.go`、`automation_delivery_proof.go`）。
- 唯一约束 `UNIQUE(rule_id, trigger_key)`：同一规则同一触发键**只有一行**。
- `status`、`attempt_count`、`error_message`、`next_retry_at`、`delivery_proof` **都是被反复覆盖的列**。

后果：一次失败经重试成功后，该次失败的现场（错误文本、当时尝试次数、当时的凭证）**永久丢失**。

**对策**：采集层必须新增 **append-only 样本存储**（独立表或独立库），且在状态被覆盖**之前**抓取。不能指望「事后查 `automation_runs` 捞历史失败」。

### 3.3 语义失误的标签来源与偏差

| 标签来源 | 覆盖 | 成本 | 固有偏差 |
| --- | --- | --- | --- |
| 买家负面话术（「退了」「投诉」） | 低 | 低 | 只覆盖激烈抱怨，沉默的错答全漏 |
| LLM-as-judge 预筛 | 高 | 中 | 自身有误判，需人工抽检校准 |
| 商家手动纠正记录 | 中 | 高 | 最准，但依赖人工操作习惯 |

**判断：语义失误必须走「judge 预筛 + 人工确认」的半自动路线。全自动不成立。**

另需评估：是否补埋「转人工 / 交回商家」信号。该信号会改变生产行为，需单独评审，不在本方案内默认实施。

## 四、建议体系形态

### 4.1 只做离线回放，不做运行时重放

**不做**：重放真实 WebSocket 消息走完整链路。
**理由**：真实链路依赖平台 API 与浏览器；滑块验证码已生产冻结（AGENTS.md §1.8，七个受保护文件），任何为回放而改动的尝试都会撞冻结项；同时触发平台风控、消耗真实账号。

**要做**：离线重放——把冻结的「对话上下文 + 三层配置快照 + 商品/订单快照」直接喂给决策链与生成接缝。

### 4.2 组件落位

| 组件 | 落位建议 | 约束依据 |
| --- | --- | --- |
| 采集器 | application 层旁路，挂在既有落库点只读消费 | 不许反向依赖上层（AGENTS.md §1.1） |
| 样本存储 | **独立库文件**，不进主 DB、不进 Git | 隔离合规风险，避免污染生产 schema |
| 回放 runner | 新增 `cmd/evalreplay`，与 `cmd/dbseed`/`dbverify`/`snapshot` 同级 | 现有 `_test.go` 跑不起大规模回放 |
| 模型注入 | 复用 `engine.AIGenerator` 接缝 + mock OpenAI server 范式 | `ai_content_eval_test.go` 已验证 |
| 门禁挂接 | 决策层进默认门禁；LLM 层只进发版门禁 | 见 §六 |

### 4.3 样本必须携带的快照

每条样本若不带全以下四项，跨版本对比即为无效实验：

1. **输入快照**：完整会话上下文（按会话为单位，不是单条消息）。
2. **配置快照**：`ai_scope_config` / `ai_knowledge_config` / `ai_policy_config` 当时取值。
3. **业务快照**：涉及的 `item_info`（价格/库存）、订单状态。
4. **模型快照**：被测模型与 judge 模型的标识、温度、采样次数。

## 五、七个风险与对策

| # | 风险 | 后果 | 对策 |
| --- | --- | --- | --- |
| 1 | **标签缺失** | 无法自动判定「答错」 | 语义失误走 judge 预筛 + 人工确认；接受半自动 |
| 2 | **失败现场易失**（§3.2） | 采不到真实历史失败 | 新增 append-only 样本存储，覆盖前抓取 |
| 3 | **幸存者偏差** | 只能算精确率，算不出通过率，测不出「把对的搞坏」 | 按比例同时存对照样本（成功案例） |
| 4 | **上下文漂移** | 同一 case 前后不可比 | 样本携带四项快照（§4.3） |
| 5 | **LLM 非确定性** | 回归门禁大量误报 | judge 固定 + temp=0.0；被测跑 N 次取多数；阈值设在噪声带之外（§七） |
| 6 | **敏感数据外泄** | 合规风险 | 评测集禁止进 Git；入库前伪名化（`logsafe.ID` 哈希 ID，正文保留格式替换值）；独立存储 |
| 7 | **样本库腐化** | 越跑越慢、指标被历史 case 拉偏 | 三层治理：核心回归集 / 滚动热点集 / 归档隔离 |

### 5.1 样本库分层治理

| 分层 | 内容 | 生命周期 |
| --- | --- | --- |
| 核心回归集 | 已修复的真实事故 case | **永久保留，禁止删除** |
| 滚动热点集 | 近 30 天高频失败 | 滚动淘汰 |
| 归档区 | 已过时（商品下架 / 话术废弃） | 标记 quarantine，不参与计分 |

## 六、分层门禁设计

| 层 | 评测内容 | 特性 | 门禁档位 |
| --- | --- | --- | --- |
| **L1 决策层** | 该不该接管 / 进哪个意图 / 是否被负向拦截 | 零账号、确定性、秒级 | **默认门禁 · 每次提交**（已有实现） |
| **L2 回放回归** | 缺陷样本喂入完整 Reply 链路，mock 模型断言 | 零账号、准确定性、分钟级 | **PR 门禁 · 合并前**（本次要建） |
| **L3 真实模型质量** | judge 打分对照基线，输出提升/回归报告 | 有成本、有噪声、分钟到小时级 | **发版门禁 · 出报告** |

要点：**不要让 LLM 评测进默认门禁。** 高成本 + 非确定性会让开发者养成「忽略门禁」的习惯，反而废掉整套机制。

## 七、指标口径与回归判定

### 7.1 噪声带原则

参照 v3 基线七轮波动 87.5%~91.0% 的实测经验：LLM 评测**天生有噪声带**。因此：

| 判定对象 | 判定方式 | 理由 |
| --- | --- | --- |
| **总分** | 阈值设在噪声带之外，超界即门禁失败 | 抗噪，可拦截真实劣化 |
| **单条 case 由通过转失败** | 只做**降级告警**，不拦截 | 逐条严格 diff 会产生海量误报 |

这是本方案与「普通回归测试」最本质的区别：**总分做门禁，单条做告警。**

### 7.2 必须声明的口径

每次评测报告必须写清（沿用 `docs/architecture/core-chain-coverage.md` 的声明纪律）：

- 被测模型与 judge 模型的标识、温度、每个样本的采样次数。
- 样本总体规模与各分层占比。
- 执行命令与是否启用浏览器集成开关。
- 与基线的对照窗口（上一个 tag / 上一次发版）。

## 八、落地路径

按风险递增、可随时中止的顺序推进。**P0 完全只读，不改任何生产行为。**

| 阶段 | 动作 | 产出 | 侵入性 |
| --- | --- | --- | --- |
| **P0** | 写只读导出脚本：从 `automation_runs` 当前态 + 日志筛候选失败样本，生成清单 | candidates 清单（不落库） | 零 |
| **P1** | judge 预筛 + 人工复核，形成 golden set v1（建议 50~100 条，覆盖主要失败类） | 脱敏样本库 v1 + 标签 | 零（离线） |
| **P2** | 建 `cmd/evalreplay`（L2），样本喂入 mock 模型链路，输出指标 | L2 runner + PR 门禁 | 中（新增代码，不改生产） |
| **P3** | 接 L3 真实模型评测，对照基线出报告；接入发版流程 | 提升/回归报告 | 中 |
| **P4** | 闭环到三层配置调优；补对照样本；建立 case 生命周期治理 | 常态化机制 | 低 |

### 8.1 高性价比切入点：事故即样本

**每次修复线上失误时，顺手把当时的输入快照固化为一条回归 case。**

样本库因此随事故自然增长，边际成本最低、价值最高——这是本项目唯一能低成本起步，且不需要先建整套采集基建的路径。

### 8.2 实施纪律

- 真正开工时按 AGENTS.md §0.6 新建 worktree，禁止在主工作区开发。
- 采集器不得反向依赖上层；`internal/agent` 的依赖禁令（§1.1）同样适用于回放相关的任何新代码。
- 任何涉及滑块验证码的实现改动一律禁止（§1.8）。

## 九、与既有方案的关系

本方案**不替代** `docs/agent-evaluation-plan.md`，而是补齐其最弱的一环：

| 维度 | 既有方案（v1.0，2026-09-21） | 本方案补强 |
| --- | --- | --- |
| 评测集来源 | 430 条真实消息一次性分类 + 手写脱敏短句 | **持续积累**的真实缺陷库 |
| 数据形态 | 静态、一次性 | 动态、带生命周期治理 |
| 采集机制 | 无（依赖人工整理快照） | 旁路采集 + append-only 存储 |
| 回归判定 | 未定义噪声处理 | 噪声带 + 总分门禁 / 单条告警 |
| 门禁档位 | 决策层进默认门禁（已明确） | 补 L2/L3 档位与触发时机 |

既有方案的五类指标与三层门禁骨架**继续有效**，本方案的改动集中在「评测集从哪来」与「指标怎么判」。
