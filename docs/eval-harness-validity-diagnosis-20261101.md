# 评测有效性诊断：为什么 80% 跑分与真实体感背离

> 版本：1.0 ｜ 日期：2026-11-01
> 关联：[客服回复有效性综合报告](customer-service-reply-effectiveness-review-20261101.md)、[评测机制方案](agent-evaluation-plan.md)
> 取证：`internal/evalharness/*`（samples/judge/runner/metric）、`cmd/evalexport/main.go`、`cmd/evalsynth/main.go`、`internal/engine/prompt_snapshot.go`、`data/evalexport/*.jsonl`

---

## 一、结论先行

1. **跑分过程存在结构性缺陷**，当前 80% 不能代表线上真实质量。已定位 7 处可复现的口径问题。
2. **"增量问题多"是真实存在的**，但它**不是体感差的主因**。主因是两件事叠加：
   - **评测没在测那些增量问题**（把"没测到的"算成了"通过"）；
   - **线上跑的是旧二进制**（连已修的都未生效）。
3. **方向性反证**：12 条真实会话中 **10 条被人工纠正**（生产确实答错），但同一批样本在评测里 **11/12 通过（91.7%）**。评测结论与人工结论**方向相反**——这足以证明评测测的不是"该事故是否复现并修复"。

## 二、跑分过程的 7 处问题（附代码证据）

### 问题 1〔致命〕触发消息取了"最后一条买家消息"，不是"出错的那句"

`cmd/evalexport/main.go:buildSnapshot` 取会话中**最后一条**买家文本作为回放触发消息：

```go
for _, item := range session.Messages {
    if item.Direction == "incoming" && item.MessageType == "text" { lastBuyerText = item.Content }
}
```

后果：会话里真正被人工纠正的那句被后续闲聊覆盖，评测去回答一句无害的话。逐条实证（12 条真实会话）：

| 会话 | 出错问句（人工纠正处） | 实际回放触发 | Takeover/Intent | 是否测到故障 |
|---|---|---|---|---|
| #4 | 全集共多少集？ | 支持复制粘贴到百度网盘吗？ | False / chitchat | **否** |
| #5 | 包含 1-47 全集嘛 | 已经买了 | False / chitchat | **否** |
| #7 | 夸克网盘有吗 | 没有吗 | False / chitchat | **否** |
| #8 | 那能退吗？（退款误判） | 这么久呀 那不太能等了 | False / chitchat | **否** |
| #11 | 发网盘吗 | 全集？ | True / stock | 部分 |
| 其余 7 条 | 与触发一致 | 与触发一致 | True / delivery|stock | 是 |

**4 条真实故障的问句被完全替换**，且判定为"不接管/闲聊"，模型随口一答就过。

### 问题 2〔致命〕用"当前代码"重建提示，等于用修复后的提示去测修复前的故障

`internal/engine/prompt_snapshot.go:ExportPromptSnapshot` 每次都用**当前** `buildSystemPrompt` + **当前** `deliveryAnswerConstraint` + **当前** `loadLiveKnowledge` 重建 system prompt。而原始故障是**旧提示**（含冲突 FAQ、无约束）造成的。于是：

- 评测看到的是 10-11 已加约束、已注入事实的"好提示"；
- 生产当时看到的是冲突提示；
- **两者不是同一个输入**，通过率自然更高。

这是典型的"用修复去重建测试"反模式。

### 问题 3 真实样本没有 golden 期望，全交给 LLM judge

`cmd/evalexport/main.go:writeSamples` 写样本时**不写 `expectation` 字段**。`samples.go:deriveExpectation` 只在"提示声明了确定发货渠道"这一种情形下推导强期望，其余返回 `nil` → 回落 `JudgeByModel`。

结果：**12 条真实样本几乎全部依赖软 judge**，没有"标准答案"可比对。

### 问题 4 judge = 被测同款模型，且没有独立 ground truth

- `modelconfig.go` / baseline 显示 `Model = JudgeModel = deepseek-flash`：**自己判自己**，存在自我偏好与宽纵。
- `judge.go:judgeUserPrompt` 只把 `KnowledgeContext`（**当初注入的那份上下文**）给 judge 看。若这份上下文本身是错的（如冲突 FAQ），judge 会把"忠实复述错误上下文"判为"一致"→ **复现同一盲区**。
- judge 标准是软性的（"正面回答/语气友好/简洁"），对"回避但礼貌"的回答天然宽容。

### 问题 5 judge 失败退出分母，通过率被放大

`metric.go:ComputeReport`：

```go
for _, caseResult := range cases {
    if caseResult.JudgeFailed { rep.JudgeFailures++; continue }  // 先 continue
    rep.Total++                                                   // 才进分母
```

判定失败（模型不返回可解析 JSON、调用失败）的样本**从分母消失**。越是难的样本越容易让 judge 输出异常，结果是"难样本蒸发 → 通过率虚高"。

### 问题 6 决策层与内容层混算，且真实样本根本没触发决策层

`runner.go:evalOne` 的决策层仅在 `exp.MustNotTakeover != nil` 时启用。真实样本无 expectation → **决策层从不触发**。于是那 4 条"不接管/闲聊"的样本仍被送去"生成 + judge"，模型答一句闲聊就通过；而合成样本里有明确 `must_not_takeover` 的决策层样本，两者被**混进同一个 pass_rate**，稀释了真实难度。

### 问题 7 单采样 + 合成样本全是手写单轮

- `samples_per_case = 1`（多数基线），非确定性未抑制。
- 合成样本由 `cmd/evalsynth` 读 `testdata/eval-scenarios.json` 生成，**全是单轮、干净、可直答**的问句（"这款发什么网盘""支持网盘发货吗"），不含多轮、已付款状态、歧义、凭证质量等真实长尾。

## 三、"体感差"的归因（三层，带权重）

| 层 | 是否是主因 | 证据 | 说明 |
|---|---|---|---|
| **A 评测失真** | **是（主因之一）** | 问题 1–6；12 真实 10 错 vs 评测 91.7% 过 | 80% 是"用修复后提示回答最后一句"的分数 |
| **B 覆盖不足（增量长尾）** | 是（次要但真实） | 合成样本全单轮；退款-履约歧义/凭证乱码/多轮状态未覆盖 | "增量问题多"成立，但它们**根本没进评测**，所以没拉低分数 |
| **C 部署缺口** | **是（主因之一）** | 线上镜像 10-12 构建，不含 10-12 后代码 | 连已修的都没上线，体感自然差 |

**直接回答**：体感差**不只是**"增量问题多"。
- 若只是增量多，那么"已覆盖的真实故障"应当能稳定通过；事实是这些故障**连测都没被测到**（问题 1）或用修复后提示测（问题 2）。
- 真正的链条是：**评测没看在错误的点上（A）→ 线上也没修好（C）→ 而真实的增量长尾又没进评测（B）**。三者叠加，才有"80 分但很难用"。

## 四、修正评测的可执行方案

按优先级：

1. **触发消息改为事故消息**：以 `human-correction` 对应的那条买家消息为触发；或**每个会话逐条买家消息各成一条样本**（推荐，能同时覆盖多轮）。
2. **固定"事故时点原始 prompt"**：导出时**存档当次真实 system prompt**（或存当时的 scope/knowledge 配置快照），评测用它回放，不要用当前代码重建。
3. **真实样本补 golden 期望**：人工写 `must_contain_any` / `must_not_contain` / `must_not_takeover`；至少让"是否直答渠道/是否回避/是否误判退款"可机检。
4. **judge 独立化**：换更强模型（如 deepseek-v4-pro 级别）、温度 0；给 judge **独立事实**而非仅注入上下文；双 judge 取一致，算一致率。
5. **judge 失败单列**：计入分母为失败，或单独报 `judge_failure_rate`，不让其消失。
6. **分层报分**：决策层（接管）与内容层（作答）**分开出分**，不混算。
7. **合成样本补长尾 + 多采样**：补多轮、已付款/已发货前置、退款歧义、凭证质量、归属反向；`samples_per_case ≥ 3` 取多数。

## 五、修正后的预期分数

> 估计口径：把问题 1（4 条故障问句复原）+ 问题 2（改回事故时点提示）叠加，12 条真实里预计 **7~9 条会重新暴露失败**。

| 口径 | 当前 | 修正后（估计） | 说明 |
|---|---|---|---|
| 12 真实（当前口径） | 91.7% | **约 50~65%** | 故障问句复原 + 原提示回放 |
| 60 条合成混算 | 80.0% | **约 55~70%** | 去掉宽松 judge 与分母蒸发 |
| 与"体感"一致性 | 背离 | **基本一致** | 这才是可据以优化的真实基线 |

**结论**：修正后分数会明显下降，但那是**更接近体感的真实基线**。在此之前，不应把 80% 当作"质量已达 80%"对外表述。

---

## 六、一句话总结

跑分不是"虚高一点"，而是**测错了对象**：它用"修复后的提示"去回答"不是出错的那句话"，再用"同款模型 + 无标准答案"的宽松 judge 判通过，还把判定失败的难样本从分母里删掉。所以 80% 与体感背离是**结构性的**，不是运气。**"增量问题多"确实存在，但它是"没被测到"，而不是"被测到且通过"**。修好评测口径后，分数会掉下来——那时它才是能驱动优化的真数字。

## 七、修复实施记录（2026-11-01 同日落地）

诊断出的 7 处问题中 6 处已改为代码，1 处（真实样本无金标准）保留了结构性限制、改用确定性推导缓解。

| # | 问题 | 改法 | 落点 |
|---|---|---|---|
| 1 | 触发消息取会话最后一条买家消息 | 新增 `selectIncidentBuyerText`：优先取「卖家否定/回避话术之前」的买家问句；并新增 `-per-message` 把整会话按每条买家消息展开 | `cmd/evalexport/main.go`、`internal/evalharness/samples.go` |
| 2 | 提示用「当前代码」重建而非事发时提示 | 未改（快照无法复原历史提示）；改由 #3 的确定性期望抵消其影响，并在报告标明为已知限制 | — |
| 3 | 真实样本无金标准，全靠软 judge | 新增 `deriveItemFactExpectation`：提示含「本商品确定事实」时，禁止「以商品详情为准 / 详情里没标注 / 我这边也说不准」 | `internal/evalharness/samples.go` |
| 4 | judge 与被测模型共模 | 新增盲评：`JudgeBlind` 默认开启，判定提示不再传入被测模型被注入的知识上下文 | `internal/evalharness/judge.go`、`config.go` |
| 5 | 判定失败被 `continue` 出分母 | 判定失败按未通过计入分母，并单列 `JudgeFailureRate` | `internal/evalharness/metric.go` |
| 6 | 决策层与内容层混算 | 拆出 `ContentPassRate` / `DecisionPassRate`；报告表新增三行 | `metric.go`、`report.go` |
| 7 | 单次采样 | `defaultSamplesPerCase` 1 → 3 | `config.go` |

附带修掉一个口径污染：自检模式（`-dry-run`）此前会拿历史回复去和「真实模型基线」比通过率，必然产出「暴跌 66 个百分点」的假警报。现在自检模式不加载基线、也不打印门禁说明。

### 7.1 验证结果（离线可复现）

```
go run ./cmd/evalreplay -root . -samples data/evalexport/samples-all.jsonl -dry-run -per-message
```

- 样本数 60 → **70**：5 个多轮会话被展开为 15 条，多出的 10 条是此前**从未被测过**的买家问句。
- 可机检期望命中 **9 条，9 条全失败**，失败原因全部是同一种话术：
  - 「这款是双盘发货的，具体是哪个网盘以商品详情和拍下后的发货消息为准哦」
  - 「具体集数商品详情里没标注，我这边也说不准」
  - 「不同商品发货方式不一样，具体以商品详情和拍下后的发货消息为准」
- 这 9 条正是商家人工纠正过的那批会话。**旧口径下它们被判通过**（soft judge 看到同一份被污染的知识上下文，认为「以详情为准」是合理回避），新口径下变成确定性失败。
- 自检模式通过率 8.6% **不可当作分数**：dry-run 用历史回复代替生成，55/70 条因「无历史 AI 回复」判失败。它只证明规则层能跑通、能抓住那 9 条。

### 7.2 仍未解决

- 真实模型分数需要能连库或用 `EVAL_*` 覆盖配置才能跑；本机两者都没有，因此**本轮没有任何新的真实分数**。旧口径的 80.0%（60 条）与修复后的真实分数不可比。
- 逐条展开对「同一会话内上下文依赖强」的问句会偏严（例：`557c4e1cd061` 的第 16 条依赖前面的成交过程）。这些样本的清空期望策略只能避免用错期望，不能补回上下文语义，仍需人工抽检。
