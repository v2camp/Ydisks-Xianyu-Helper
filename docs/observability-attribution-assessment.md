# 可观测性与归因能力评估

> 日期：2026-10-11
> 关联：`docs/traffic-replay-evaluation-plan.md`（评测方案）、`docs/eval-replay-runbook.md`（运行手册）
> 结论摘要：**现状不满足归因诉求**。本次已落地 P0（决策归因），P1~P3 为后续排期项。

## 一、结论

评测体系把"通过率"变成了可度量的数字，但当某条样本失败时，**当前系统无法回答"为什么"**。
根因有两类，且都不是模型问题：

1. **不接管的消息完全无痕**——`Reply` 在接管判定为假时直接 `return nil, nil`，既不落库也不记日志。
2. **历史现场不可还原**——系统提示不落库，事后只能用**当前**配置重建。重建结果与事发当时可能不同，
   评测据此归因会得出错误结论（本次扩充评测时已实际踩到，见 §五）。

## 二、现状盘点

### 2.1 AI 客服链路

| 环节 | 现有记录 | 能回答什么 |
|---|---|---|
| 决策 | `ai_conversations`（8 字段：账号/会话/商品/角色/内容/意图/砍价轮次/时间） | 买家问了什么、AI 答了什么、粗粒度意图标签 |
| 不接管 | **无** | — |
| 生成 | 无独立记录；模型名只在配置表 | — |
| 守卫 | `logger.Warn("AI 报价超过折扣边界")` | 仅日志，且会随保留期轮转 |
| Agent 工具 | `logger.Warn("客服 Agent 工具调用失败")` | 仅失败，无轨迹 |

### 2.2 自动发货链路

`automation_runs` 有 `status`、`error_message`、`attempt_count`、`next_retry_at`、`delivery_proof`、`raw_event_json`。

| 能回答什么 | 说明 |
|---|---|
| 最终成功与否 | `status` |
| 失败原因 | `error_message`，`NoRetryErrorPrefix` 区分永久失败与可重试 |
| 重试了几次 | `attempt_count` |

**但回答不了"卡在哪一步"**——规则匹配、卡密选择、消息动作、凭证发送四个阶段没有分别留痕。
更关键的是：**`status = success` 只代表动作调用返回成功，不代表买家实际收到**。
平台静默拦截（限流、敏感词）时系统记为成功，而买家侧什么都没收到，这类纠纷当前无法被发现。

### 2.3 结构性限制

`automation_runs` 是**可变当前态表**（`INSERT IGNORE` + `UPDATE`，`UNIQUE(rule_id, trigger_key)` 单行），
失败现场经重试后被覆盖。这是发货链路归因的硬约束：不能事后查表捞历史，必须当时留痕。

## 三、归因诉求与缺口对照

评测失败时需要回答的问题，逐项对照：

| 归因问题 | 现状 | 缺口 |
|---|---|---|
| 这条消息为什么被 AI 接管？ | 只能靠配置反推 | **P0** |
| 这条消息为什么没被接管？ | 完全无记录 | **P0** |
| 是模型波动还是配置变更导致？ | 无配置版本信息 | **P0**（配置指纹） |
| 模型当时看到的完整提示是什么？ | 只能用当前配置重建 | **P1** |
| 模型生成了什么、被哪条规则改写？ | 无原始输出、无守卫记录 | **P1** |
| Agent 调用了哪些工具、为何失败？ | 仅失败日志 | **P2** |
| 发货卡在哪一步？ | 无步骤级留痕 | **P3** |
| 系统说"已发货"，买家收到了吗？ | 无买家侧确认信号 | **P3** |

## 四、分层升级方案

### P0 决策归因（本次已落地）

新增 `ai_decision_log` 表（迁移 `00064`），**接管与不接管都留痕**：

| 字段 | 作用 |
|---|---|
| `takeover` | 最终是否接管 |
| `hit_intents` | 命中的意图名，按判定顺序 |
| `negative_hit` / `extra_hit` | 是否被内置/配置负向词、扩展词表拦截 |
| `intent_label` | 写入历史的意图标签 |
| `reason` | 原因简码：`taken` / `no-intent` / `negative` / `extra-negative` |
| `config_fingerprint` | 判定所用边界配置的指纹 |
| `message_hash` / `message_preview` | 消息哈希与 60 字预览 |

设计取舍：

- **消息只存哈希与短预览**，不复制完整对话到审计表，规避隐私与体积问题。
- **配置指纹**用内置词表 + 配置原文 + 各意图的开关与组合词计算（不含敏感值）。
  归因时对比指纹即可区分「模型波动」与「配置变更」，避免把配置改动误判成模型退化。
- **埋点失败只记 Debug**，绝不阻断回复链路；可观测性不得影响主流程。

### P1 生成归因（待排期）

新增 `ai_generation_log`：模型标识、提示指纹、提示全文（可选）、输入长度、
原始输出、可见输出、耗时、token 用量、被价格守卫拦截与否及原因、错误分类。

注意体积与敏感：提示中含商品原始 JSON，建议默认只存哈希，需要时按会话临时重建。

### P2 Agent 轨迹（待排期）

新增 `ai_tool_call_log`：回合序号、工具名、参数哈希、结果摘要、耗时、
capability 放行决策。当前只有失败日志，无法回答"Agent 到底查了什么"。

### P3 发货链路步骤化（待排期）

新增 `automation_run_steps`：`run_id`、阶段（规则匹配 / 卡密选择 / 消息动作 / 凭证发送）、
每步状态、错误、耗时。同时建议引入**买家侧确认信号**（如买家回复"收到了"）
与静默失败检测（动作成功但长时间无送达反馈），否则 `success` 会持续掩盖真实丢件。

## 五、本次评估暴露的一个方法论教训

扩充评测样本时发现：**期望推导原先只识别新格式提示**，导致提示词格式一变，判定口径随之改变，
同一批样本在"规则判定"与"模型判定"之间漂移，修复前后的评测结果无法对照。

更深一层的问题是：**system prompt 不落库，使"当时的提示"不可还原**。
我们只能用当前代码重建历史样本的提示，这本身就引入了偏差。

这直接支撑 P1 的必要性——**没有提示留痕，任何跨版本的归因都建立在重建之上，而重建不等于事实**。

## 六、落地建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 已完成 | 决策归因是评测排查的第一需求 |
| P1 | 建议尽快 | 跨版本归因的前提，否则结论不可靠 |
| P2 | 按需 | 仅在 Agent 工具调用成为主要失败源时需要 |
| P3 | 建议尽快 | 发货丢件当前无法被发现，风险高于收益倒挂 |
