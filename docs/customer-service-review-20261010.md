# 客服机器人运行复盘与改进思路

> 版本：1.0
> 日期：2026-10-10
> 数据来源：部署环境 PostgreSQL（`ydisks-xianyu-helper-postgres-1`）
> 关联文档：[客服 Agent 升级计划](customer-service-agent-upgrade-plan.md)（v1.0.14 已实施）
> 关联代码：`internal/engine/ai.go`、`ai_scope.go`、`ai_intent.go`、`ai_live_context.go`

## 一、摘要

配置化 AI 客服（升级计划 v1.0）上线后已具备「边界 / 语料 / 策略」三层低代码能力，**框架到位但真实接管率仍然很低**。近三天实测：

| 指标 | 实测值 | 说明 |
|---|---|---|
| AI 自动回复占比 | **6.6%**（17 / 259） | 我方消息里仅 17 条由 AI 生成，其余 93.4% 为人工 |
| 买家提问 AI 覆盖 | **20.5%**（17 / 83） | 79.5% 的提问 AI 根本不接管 |
| 发货方式类提问 | **17 条，AI 全部答非所问** | 无一给出确定答案 |
| FAQ 知识可用率 | **40%**（2 / 5 类） | 退款、更新、赠送 3 类为死知识 |
| 商品含发货渠道线索 | **0 / 31** | 推断函数恒返回空，约束被迫打太极 |
| 自动发货覆盖率 | **约 34%**（68 / 201 单） | 剩余为人工发货 |

核心结论：**瓶颈不在模型能力，而在「事实数据源」缺位 + 意图正则过窄**。
买家问的都是有确定答案的事实题（"有夸克网盘吗"），但系统没有把「商品→实际发货渠道」喂给模型，
又用一条硬性约束禁掉了模型的确定性回答，导致 AI 只能输出"以商品详情页为准"的无效话术。

> 若要做周维度趋势分析，需先确认消息保留策略（见第七章待确认项）。

## 三、运行现状

### 3.1 AI 参与度极低

我方发出的文本/图片消息 259 条，与 `ai_conversations` 中的 assistant 回复逐一比对后：

- **AI 自动生成：17 条（6.6%）**
- **人工 / 其他来源：242 条（93.4%）**

`ai_conversations` 累计仅 26 行（13 组问答），意图只有两类：`delivery` 9 条、`stock` 4 条。
**砍价（`bargain`）意图零命中**——而这恰恰是 AI 最早被允许接管的场景。

### 3.2 响应及时性：中位数可接受，长尾极重

| 指标 | 结果 |
|---|---|
| 应答率 | 94.4%（85 / 90） |
| 响应延迟中位数 | **42 秒** |
| 响应延迟均值 | 943 秒 |
| 60 秒内 | 51.8% |
| 10 分钟内 | 71.8% |
| 1 小时内 | 87.1% |

延迟超过 10 分钟的 20 个案例几乎全是人工介入（`>4000 秒`的尤其明显），典型如：
`"我还在班上，今晚回去打包明天发货哈"`、`"你好，是不要了吗？"`。

**解读**：秒级响应的部分由 AI 承担，一旦落到人工，响应时间就退化到小时级。
这不是人的问题，而是"AI 不敢接管 → 堆给人工 → 排队"的连锁效应。

### 3.3 人工在做大量重复劳动

人工回复 TOP 分布（按内容去重计数）：

| 次数 | 内容特征 |
|---|---|
| 46 | 某商品的百度网盘分享链接（固定一条） |
| 14 | 另一商品的百度网盘链接 |
| 14 | 「AI 写量化策略教程」百度网盘链接 |
| 8 | `稍等` |
| 7 / 6 | 其余两个商品的固定链接 |
| 5 | `对的` / `亲，商品使用满意的话，麻烦给个评价` |
| 4 | `转账给对方` |

**同一条链接重复发送 46 次**——合计约 87 条消息属于"搬运固定链接"，属于确定性、可完全自动化的动作。

## 四、根因链条

### 4.1 链路一：事实源缺位 → AI 只能打太极（最重要）

这是贯穿全盘的**主根因**，因果链如下：

```
31 个商品中 0 个描述含"百度/夸克/网盘"
        ↓
delivery_templates = 0、delivery_template_messages = 0
        ↓
inferDeliveryHints() 的线索语料为空 → 恒返回空串
        ↓
LiveKnowledge.DeliveryHint 为空，无法注入 system prompt
        ↓
deliveryAnswerConstraint 硬性规定：
  "无线索则回答「不同商品发货方式不同，以商品详情和拍下的发货消息为准」"
        ↓
AI 对 17 条"有夸克吗/百度吗/什么盘"类提问，全部输出同一句无效话术
```

关键代码位置：

- `internal/engine/ai_live_context.go:170` `inferDeliveryHints`
  —— 从「商品标题+描述+详情 + 发货模板消息 + 卡组名」汇总线索后检测渠道
- `internal/engine/ai_live_context.go:29` `deliveryAnswerConstraint`
  —— 硬性兜底约束，无条件追加到每次请求的 system prompt

实测 AI 的典型输出（均为同一语义）：

| 买家提问 | AI 回答（节选） |
|---|---|
| `夸克网盘吗` | 「不同商品发货方式不太一样哦，具体以商品详情和拍下后的发货消息为准～」 |
| `我要夸克的` | 「我这边先帮您确认下，您拍下后备注一下夸克，我看能不能安排~」 |
| `有度盘的吗` | 「这款是双盘发货的，具体是哪个网盘以商品详情…为准哦」 |
| `全集共多少集？` | 「具体集数商品详情里没标注，我这边也说不准，内容是全的完结版～」 |

**买家要的是"是/不是"，AI 给的是"我不知道"。** 这不是模型弱，是没给它答案。

反过来验证数据：

```sql
-- 31 个商品里，描述含渠道线索的数量
SELECT count(*) FROM item_info
WHERE item_description ILIKE '%百度%' OR item_description ILIKE '%夸克%' OR item_description ILIKE '%网盘%';
-- 结果：0
```

### 4.2 链路二：意图正则覆盖不到口语问法

现行 `ai_scope_config` 的 `delivery` 意图：

```
什么盘|网盘发货|资源码|鸿蒙|度盘|夸克|怎么发|什么时候发|多久发|发货方式|什么网盘|(百度网盘&发)
```

用生产配置回测 83 条有效提问，**66 条（79.5%）完全落空**。漏配的典型：

| 未命中提问 | 漏配原因 |
|---|---|
| `百度吗` `百度云的吗` `百度网盘吗` `百度网盘链接？` `百度网盘资源吗？` | 只认 `什么盘`，不认「X盘吗」句式 |
| `网盘吗` `发网盘吗` `度？` | 同上；`度？` 单字，`度盘` 匹配不到 |
| `全剧吗` `所有的吗` `更新完了吗` `30到34吗` | stock 意图只有 `第X季/单买/全集/完整版` |
| `还有大班的吗` `中班全册吗？` `是3本24吗？` | 商品规格咨询，product_qa 完全未覆盖 |
| `小鸡球球点读笔可以用吗` `可以试看一下吗` `这个没有时间限制吧` | 使用与时效类，无任何意图覆盖 |

**规律**：口语真实提问以「有没有 X」「X 吗」「支持 X 吗」为主，而正则只收录了书面问法「什么 X」。

### 4.3 链路三：3 条 FAQ 是死知识，且存在规则冲突

`ai_knowledge_config` 配了 5 类 FAQ：`发货`、`资源码`、`退款`、`更新`、`赠送`。
`ai_scope_config` 只有 4 个意图：`bargain`、`product_qa`、`delivery`、`stock`。

| FAQ 类别 | 是否有对应意图 | 能否触达 |
|---|---|---|
| 发货 | delivery ✓ | 可（但见 4.1） |
| 资源码 | delivery ✓ | 可 |
| **退款** | ✗ | **否** |
| **更新** | ✗ | **否** |
| **赠送** | ✗ | **否** |

更进一步，这里藏着一处**规则自相矛盾**：
`builtinComplaintPatterns`（`ai_intent.go:51`）把「退款|退货」列为负向词，命中即一票否决 AI 接管。

于是形成死锁：
> 就算给 `refund` 配上意图，`那能退吗？` 这类**售前咨询**也会先被当作**售后纠纷**拦掉，仍然进不了 AI。

实测数据中至少有 5 条售前退款咨询（`那能退吗？`、`退掉吧`、`辛苦退下款`、`看错了，我以为是黑马的，给我退了吧`、`我不买了`）被这条规则静默丢弃。

**要区分「咨询退款政策」（售前，可 AI 答）与「我要退款/投诉」（售后，转人工）。**

### 4.4 链路四：是非题回答存在逻辑缺陷

两处实测反例：

| 轮次 | 买家提问 | AI/人工回答 | 问题 |
|---|---|---|---|
| 1 | `不是脱口秀工作手册吧` | `是的` | 否定式提问，"是的"语义二义（是"你说得对"还是"它就是"？） |
| 2 | `是关于自媒体的新版吗` | `是的` | 未经核对即断言，且延迟 5028 秒 |

现有 prompt 未约束是非题的**字面确认义务**。改进成本低但直接决定信任感。

### 4.5 链路五：两个引擎长期空转

| 表 | 记录数 | 含义 |
|---|---|---|
| `keywords` | **0** | 关键字回复引擎从未配置任何规则 |
| `default_reply_records` | **0** | 默认回复从未触发过一次 |
| `delivery_templates` | **0** | 发货模板未配置 |
| `ai_bargain_quotes` | **0** | 议价报价从未生成 |

链路里保留了这三个占位环节，但长期零配置。要么补数据，要么明确下线，避免给人"已覆盖"的错觉。

## 五、改进思路

按 ROI 排序。**P0 ~ P1 两项预计可把 AI 接管率从 20.5% 提升到 50% 以上。**

### P0：建立「商品 → 发货渠道」事实源，解锁确定性回答

**依据**：4.1 全链路；17 条网盘提问零正确应答；31 商品零线索；`inferDeliveryHints` 恒空。

三项动作，缺一不可：

1. **沉淀事实数据**（最高优先级，不需改代码）
   从历史已发出的交付消息里反向抽取「商品 → 渠道」映射。
   人工 3 天发了约 87 条固定链接，已足以覆盖头部 SKU：利用 `chat_messages` 中 outgoing 文本
   出现频次最高的链接，按 `item_id` 归并即可自动建表。

2. **放宽 `deliveryAnswerConstraint`**
   现在写的是"无线索则…"，应改为：
   > 「有当前商品的确定渠道线索时，必须直接回答该渠道（如"这款发百度网盘"）；无线索时才用兜底话术。」

   判定依据是"有没有 item 级线索"，而不是简单地一刀切禁止。

3. **把事实源接进 `inferDeliveryHints`**
   让它在商品描述/发货模板之外，多查一张 `item_delivery_channel` 映射表。

**预期**：17 条网盘类提问从"我不知道"变为确定答复；连带降低"售后追问"和"人工介入"。

### P1：意图正则补齐口语问法

**依据**：4.2；66 条落空明细。

建议从「穷举词表」转向「渠道词 + 疑问句式」的组合匹配：

```
delivery: 渠道词(百度|度盘|夸克|网盘|迅雷|阿里|UC|115|天翼) & 疑问句式(吗|嘛|么|有|支持|可以|能|...)
         | (发货|怎么发|多久发|什么时候发|发网盘)
```

同时补齐三类新意图：

| 新意图 | 覆盖场景（实测原句） |
|---|---|
| `refund` | `那能退吗？` `退掉吧` `辛苦退下款` `我不买了` |
| `spec` | `还有大班的吗` `中班全册吗？` `是3本24吗？` `30到34吗` |
| `usage` | `小鸡球球点读笔可以用吗` `这个没有时间限制吧` `可以试看一下吗` `4k需要购买` |

注意 `spec`/`usage` 需要 AI 能读到商品规格，属于 P0 事实源的延伸。

### P2：解开"退款|退货"负向词的死锁

**依据**：4.3；5 条售前退款咨询被误杀。

建议在负向判定前增加前置区分：

- **售前咨询**（"能退吗""支持退款吗""不喜欢可以退吗"）→ 走 `refund` 意图，由 AI 按 FAQ 答政策；
- **售后纠纷**（"我要退款""已付款没发货""投诉"）→ 仍由负向词拦截转人工。

实现上可把负向词收窄为带动作主语的表达（`我要退|给我退|申请退款|已退款`），
让纯咨询型表达自然落到 `refund` 意图。

### P3：是非题回答约束

**依据**：4.4 两处反例。

在 system prompt 追加：

> 「对"是不是/有没有/支持吗"类是非问句，必须先给出明确的"是/不是/有/没有"，再补充依据；
> 遇到否定式提问（"不是 X 吧"），按字面含义确认，不得只回答"是的"造成二义。」

成本低、见效快，且能显著降低因答非所问产生的追问轮次。

### P4：提升发货自动化覆盖率

**依据**：自动发货 68/201 ≈ 34%；同一条链接人工重复发送 46 次；人工原话`"今天自动发货有点问题"`、`"抱歉哈，今天自动发货有点儿问题"`。

动作：优先排查自动发货的失败分支（19 个启用卡券中是否有库存/模板缺失），
把头部 SKU 补齐后做灰度，目标把 `system_shipped=1` 占比从 34% 提升到 70%。

## 六、数据一致性风险（顺带发现）

两个字段单位在同一个message上下文里混用，建议在修复上述问题的同一批次处理：

| 字段 | 单位 | 验证 |
|---|---|---|
| `chat_messages.created_at` | **秒** | 值 1791646171 → 2026-10-10 23:29 |
| `chat_messages.sent_at` | **毫秒** | 值 1791646037589 → 同上时刻 |
| `chat_sessions.last_message_at` | **毫秒** | 被当作秒读取时得到 58745 年 |

风险点：`idx_chat_sessions_account_recent ON chat_sessions(cookie_id, last_message_at DESC)`
用于按最近活跃排序，若上层有代码误按秒解析，排序会整体错乱。

## 七、待确认项

1. **消息保留策略**：为何生产库只有 3 天数据？是自动清理还是采集问题？影响能否做周/月维度趋势。
2. **347 个会话 vs 113 个有消息**：234 个会话 `last_message_at = 0`（从未产生文本），确认为正常状态还是需要排查落库丢失。
3. **模型配置双份**：`system_settings.ai_model = deepseek-flash` / `ai_api_url = api.deepseek.com`，
   而 `ai_reply_settings.model_name = qwen-plus` / `base_url = dashscope`。当前实际生效的是全局配置，
   账号级配置处于无效状态——需确认是设计如此还是配置漂移。
4. **`aiShouldHandleIntent` 疑似死代码**：该函数只在 `ai_intent_test.go` 被调用，生产链路由
   `ai_scope.go` 的 `scope.decide()` 接管。两套意图判定并存（`ai_intent.go` 的 complaint/bargain/order/inquiry/consult
   与 `ai_scope_config` 的 bargain/product_qa/delivery/stock）容易误导后续维护，建议明确取舍。

### 处置结论

| 待确认项 | 结论 | 落地 |
|---|---|---|
| 1. 消息保留策略 | 生产库仅 3 天与采集侧写入有关，代码里本无清理逻辑；新增统一保留清理任务，默认 30 天、下限 10 天，可配置，覆盖聊天消息与全部日志表（含此前完全没有清理逻辑的 `account_login_logs` / `risk_control_logs` / `security_audit_logs` / `mcp_call_audit`） | 迁移 `00062` |
| 2. 会话数 > 消息数 | **不是过滤条件问题**：347 个会话中 229 个有时间戳但消息从未回填（2024-12~2026-06 历史遗留），4 个 `last_message_at = 0`，仅 114 个有消息。存储无压力（消息表 344 kB、会话表 392 kB、整库 85 MB），无需改代码 | 仅排查结论 |
| 3. 模型配置双份 | 判定为配置漂移并彻底收口：账号级模型三列（`model_name` / `api_key` / `base_url`）写入侧早已停写、消费侧零读取，现从代码与表结构中一并移除；模型配置单一来源 = `system_settings` 全局 AI 配置 | 迁移 `00063` |
| 4. `aiShouldHandleIntent` 死代码 | 确认为死代码，连同整张意图注册表（`classifyIntent` / `aiIntentRules` / `buildComplaintPatterns` 等）一并移除；生产路径保持不变，仍由 `ai_scope.go` 的 `scope.decide()` 接管 | 已随客服 Agent 改进分支合入 main |

用户批复同时决定：模型配置**保留生效的全局配置**（`system_settings` 的 deepseek-flash 一套）；月度趋势暂不做，**先看周趋势**；自动发货相关问题**暂缓**，后续单独起任务做 badcase 回放，保证关键场景不回归。
