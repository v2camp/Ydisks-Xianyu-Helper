# 智能客服「启停与应答正确性」专项诊断

> 日期：2026-10-31
> 承接：[2026-10-31 周复盘](customer-service-weekly-review-20261031.md)、[2026-10-18 ROI 报告](customer-service-roi-optimization-20261018.md)
> 取证：① 源码判定链（definitive）；② `backup/xianyu-backup-20261008-1018.sql` 生产快照（10-08，含真实 `ai_reply_settings`/`system_settings`/`default_replies`/`keywords`，密钥已屏蔽）；③ `data/evalexport` 12 条真实会话（10-09~10）
> 结论口径：**"是否启用"与"是否答对"是两个独立问题，且都随配置与时间变化，不能一句话定论。**

---

## 一、结论先行

1. **"启用"有两层，任一为否 AI 就不介入**：① 账号级总开关 `ai_reply_settings.ai_enabled`；② 每条消息的准入门禁（归属/意图/负向词/凭据）。前者是"开没开"，后者是"开了但这条轮不轮到"——用户看到的"没回复"往往二者混合。
2. **唯一可取证的 10-08 生产快照显示：AI 未启用**——`ai_reply_settings` 0 行、`system_settings.ai_api_key` 为空、`default_replies` 0 行、`keywords` 0 行、仅 2 个账号。即该时点**连模板通道都没配，只有人工在答**。
3. **但 10-18 ROI 报告记录"线上已能正确答出『这款发的是百度网盘』"**——说明 10-08~10-18 之间 AI 被启用过。因此"是否启用"是**时间窗口问题**：历史确实存在"未启用"期，之后启用过，当前线上状态**无法在本沙箱直读**（生产库不可达）。
4. **即便启用，12 条真实会话显示"答不对"是系统性而非偶发**：回避话术 7/12、同商品规格自相矛盾、退款意图误判、凭证乱码重复外发。根因分四层（事实/提示词/意图/策略），且**归因表 0 行使"答对率"无法量化**。

---

## 二、启用判定的四道闸门（代码级，确定性）

AI 回复的完整执行链：`message_dispatcher` → `canAutoReply`（归属门禁）→ `ReplyService.resolve`（API→关键词→插件→**AI**→默认）→ `AIReplierImpl.Reply`（账号开关 → 负向/意图 → 凭据 → 生成 → 价格守卫）。四道闸门任一不过即"不回复"：

| 闸门 | 位置 | 触发即不介入的条件 | 可取证依据 |
|---|---|---|---|
| **G1 归属门禁** | `message_dispatcher.go:333`、`reply_identity.go:82-96` | 商品不在本地 `item_info`、归属查询失败、账号为 buyer、selfID 缺失 → **四通道（关键词/插件/AI/默认）一起跳过** | ROI §3.4：近 24h 4 次「商品不在当前账号本地商品清单，跳过自动回复」 |
| **G2 账号总开关** | `ai.go:66`、`ai_reply.go:84-106` | `ai_reply_settings` 无该账号行（`ErrNotFound`）或 `ai_enabled=0` → `Reply` 返回 nil | **10-08 快照：`ai_reply_settings` 0 行** |
| **G3 边界（负向+意图）** | `ai.go:83-97`、`ai_scope.go:268-283` | 负向词命中 → 一票否决；或**未命中任何 `allowAI` 意图** → `takeover=false`；空配置回落内置（仅砍价） | ROI §2.3/§3.2：线上 4 意图 vs 代码 8 意图；delivery 词表逐字等于 10-10 旧版 |
| **G4 凭据** | `ai.go:104-107`、`globalAIConfig` | `ai_api_key` 为空 → 记「AI 已启用但未配置 APIKey」并返回 nil | **10-08 快照：`system_settings.ai_api_key` 为空** |

> 关键语义：`AIReply.Get` 对无行返回 `ErrNotFound`，`ai.go` 判 `err != nil || cfg == nil` 即视为未启用——所以**"表里没有这一行"等价于"没开 AI"**，不是"用默认配置开"。

## 三、"为什么没启用"——按闸门给候选根因

区分两类，避免把"没轮到"误判成"没开"：

**A. 真·没启用（G2/G4）**
- **G2 账号级未开 AI**：10-08 快照 0 行，实证。可能原因：从未在 Web UI 打开该账号 AI 回复开关，或写入失败。
- **G4 凭据缺失**：10-08 `ai_api_key` 为空，实证。即使 `ai_enabled=1`，无 key 也不生成，只在日志留一条 Warn（**静默**，无告警）。

**B. 启用了但没轮到（G1/G3）**
- **G1 商品同步停摆 → 归属门禁整条跳过**：ROI §3.4 实证（`item_info` 停在 10-11、6 次`令牌为空`、4 次"跳过自动回复"）。这是最前置的阻断点，且**不只拦 AI，四通道全拦**。
- **G3 意图未命中/负向词**：线上仅 4 意图（代码 8），大量口语问法（"百度吗""是网盘吗""多少集"）不命中 → `takeover=false`。用户感受与"没启用"完全相同，但本质是覆盖不足。

**判读规则**：若某会话"完全无回复"，优先 G1（商品不在库）；若"有回复但答非所问/回避"，则 AI 已介入，问题在内容层（见第四节）。

## 四、"启用了是否答对 / 为什么没答对"

### 4.1 实证：12 条真实会话中的答不对模式

| 模式 | 会话 | 具体用户消息 → 错误回答 | 占比 |
|---|---|---|---|
| **回避是非题** | `[1][3][8][9][11][6][12]` | 「有度盘的吗」→「具体哪个网盘以商品详情和拍下后的发货消息为准哦」，人工纠正「机器人瞎回复，双盘就是度盘+夸」 | **7/12** |
| **规格自相矛盾** | `[4]` vs `[7][10]` | 「全集共多少集？」→「说不准」；同商品别处→「34集全」 | 同商品摇摆 |
| **退款意图误判** | `[12]` | 「那能退吗？」→「如果你能等，我可以帮你导一下」（读成"等导夸克"，退款意图未触发） | 1 例（严重） |
| **凭证乱码+重复** | `[2][3][4][6][7][10][12]` | 外发含 `祄七三及森并闭里品` 平台水印乱码；同凭证连发 2~3 次 | 普遍 |

### 4.2 为什么没答对——四层根因

1. **事实层（grounding 无据）**：`grounding_source` 若落在 `item-text`/`none`，说明模型没有卡密渠道事实（`card-channel`）、无规格事实、无订单履约事实 → 只能回避或猜。这是"答不对"的第一性原因。
2. **提示词层（指令冲突）**：知识库 FAQ「不同商品发货方式不同，请以商品详情页说明为准」被标为「必须以此为据」，与 `deliveryAnswerConstraint`（"优先于店铺通用说明"）**同一次注入里相互冲突** → 模型在两段相反指引间摇摆，复述了回避话术。这是 10-11 事故的残留，10-18 已改文案但**需镜像发布才生效**。
3. **意图层（优先级歧义）**：`refund` 与 `fulfillment`/安抚话术在"没拿到想要渠道"语境下优先级不清，`[12]`「能退吗」被履约安抚顶替。
4. **策略层（模型产出被整段替换）**：价格守卫命中时 `answer_source` 变为 `policy-no-discount`/`policy-min-price`，文本仍流畅，**看起来像模型答的，其实不是**。不记录来源就会把策略产出误当模型能力来评价。
5. **归因层（无法量化）**：`ai_decision_log`/`ai_generation_log` 自部署起 0 行（`bool→INTEGER` 编码失败，代码已修但镜像未发布）→ **"答对率"没有分母**，只能用 12 条人工标注做定性判断。

## 五、把"启用/答对"从推断变事实：可执行验证清单

按依赖顺序执行，每步都锚定既有机制，不新建链路：

1. **确认账号级启用态（G2/G4）**：只读查 `SELECT cookie_id, ai_enabled FROM ai_reply_settings;` 与 `ai_api_key` 是否非空。若为空 → 先补开关与密钥，这是"根本没启用"的直接判据。
2. **发布镜像（承接 N2）**：让归因布尔修复、负向词、商品事实、订单履约、FAQ 文案真正上线。**发布前所有"答对率"结论都是推断**。
3. **跑归因分布（承接 N5）**：用 `docs/attribution-queries.md` 的 SQL 出 `answer_source` 与 `grounding_source` 分布。
   - `grounding_source` 大量 `item-text` → 卡密未绑定到自动化规则，渠道仍在猜，而非事实。
   - `answer_source` 大量 `policy-*` → 大量回答其实是价格守卫替换，不是模型能力。
   - `answer_source=empty` → 模型无产出（硬故障），需单独排查。
4. **区分"没轮到"与"没答对"（承接 G1/G3）**：`ai_decision_log.reason` 分布——`negative`（负向拦截）、`no-intent`（意图未命中）、`takeover=1` 三类比例，直接回答"多少消息 AI 根本没接手"。

## 七、一句话回答四个子问题

- **是否启用？** 分账号级开关（G2）与消息准入（G1/G3）两层；10-08 快照显示**未启用**，10-18 起曾启用，当前线上态需只读查库确认。
- **为什么没启用？** 真没开：`ai_enabled=0`/无行、`api_key` 空；开了没轮到：商品不在本地库（G1）、意图未命中/负向词（G3）。
- **启用了是否答对？** 12 条真实会话显示**系统性答不对**（回避 7/12、规格矛盾、退款误判、凭证乱码重复）。
- **为什么没答对？** 事实未注入（无 card-channel/规格/履约）→ 提示词指令冲突（FAQ"以详情页为准" vs 发货约束）→ 意图优先级歧义（退款 vs 履约）→ 价格守卫整段替换；且归因表 0 行使答对率无法量化。
