## 一、数据口径与说明

### 1.1 时间窗口与样本构成

任务要求检查"近一周（过去 7 天）"的客服消息。本运行环境无法直连生产数据库，可获取的最近一批客服消息记录是 **2026-10-11 的事故样本快照**，覆盖生产会话的实际发生时间 **2026-10-09 ~ 2026-10-10**（落在近一周窗口的前段）。这与 2026-10-10 复盘已发现的"生产库仅保留数天消息"现象一致（消息保留策略见复盘文档第七章，已由迁移 `00062` 统一收口为默认 30 天）。

本批样本由 `cmd/evalexport` 只读导出，账号/会话标识已哈希脱敏，正文中不出现明文凭证。构成如下：

| 样本集 | 文件 | 条数 | 性质 |
|---|---|---|---|
| 真实生产事故样本 | `samples.jsonl` | 12 | 生产真实会话，命中"人工纠正"信号 10 条 |
| 合成覆盖探针 | `samples-synthetic.jsonl` | 48 | 按 9 大能力维度构造的覆盖探针 |
| 合并样本库 | `samples-all.jsonl` | 60 | 上述两类合并并打场景分组标签（12 真实与其重合） |

> ⚠️ 有效结论以 **12 条真实生产样本**为最高置信依据（等价于商家手工标注），48 条合成探针用于揭示能力覆盖缺口。合成样本不构成"已发生故障"的证据，仅表示"该维度当前大概率答不好"。

### 1.2 判定信号

`cmd/evalexport` 的 `classify()` 按启发式给出事故标签，最高置信信号为 `human-correction`（商家在会话中明确否定机器人回复，或人工接手重答）。真实样本中 **10/12 命中该信号**，且全部集中在"发货渠道 / 目录库存"类会话 —— 即事实源缺位最直接的会话。

### 1.3 评测维度分布（合成 + 真实合并标记）

| 场景分组 | 样本数 | 含义 |
|---|---|---|
| link-code | 18 | 网盘链接 / 提取码类高频诉求 |
| delivery | 14 | 发货渠道问答 |
| compliance | 14 | 合规承诺（退换 / 发票 / 包邮 / 赠品） |
| escalation | 12 | 必须转人工的表达（退款 / 投诉 / 举报） |
| robustness | 12 | 闲聊 / 无意义输入鲁棒性 |
| bargain | 10 | 砍价议价 |
| catalog | 8 | 商品目录 / 规格咨询 |
| fulfillment | 8 | 自动发货履约（付款未收到 / 重发） |
| order | 6 | 订单状态 / 物流 / 改地址 |

## 二、核心结论

**瓶颈不在模型能力，而在"事实数据源"缺位 + 意图判定与事实注入的耦合失配。** 这与 2026-10-10 复盘的核心结论一致，本轮用真实生产样本进一步坐实：

1. **发货渠道答非所问是头号问题**：买家问"有 X 盘吗 / 发网盘吗"，机器人恒回复"以商品详情和拍下后的发货消息为准"，把是非题答成"我不知道"。真实样本中该模式占人工纠正的绝大多数。
2. **目录 / 库存事实前后矛盾**：同一商品，有时答"说不准"，有时却答"34 集全集"，说明机器人没有稳定的商品事实源，只能凭提示词里零散的商品标题猜测。
3. **意图误分流**：发货类问题（"发网盘吗"）被错分到 `stock` 意图，导致回答偏题。
4. **已落地的提示词修复只解决"有事实时敢答"，没解决"事实从哪来"**：快照显示 `deliveryAnswerConstraint` 已改写为"有确定渠道时必须直接回答"，但 `inferDeliveryHints()` 仍因商品描述无渠道关键词而恒返回空，绝大多数发货场景仍无事实可注入。

## 三、问题清单（按严重度与频次）

### 3.1 准确性类（最高优先级）

**问题 A：发货渠道恒用回避话术，是非题答成"不知道"**
- 代表用户消息：`有度盘的吗`、`夸克？`、`有夸克网盘的吗`、`有夸克嘛`、`你好想问下有夸克的嘛`、`发网盘吗`
- 机器人错误回答（节选）：
  - 「不同商品发货方式不一样哈，具体以商品详情页说明和拍下后的发货消息为准～」
  - 「亲，不同商品发货方式不一样哦，具体以商品详情和拍下后的发货消息为准～」
  - 「您好～这款是双盘发货的，具体是哪个网盘以商品详情和拍下后的发货消息为准哦」
- 人工纠正（脱敏）：`机器人瞎回复，双盘就是度盘+夸`
- 说明：即便意图已正确识别为 `delivery` 并接管，机器人仍输出回避话术。根因是 `inferDeliveryHints()` 返回空、`LiveKnowledge.DeliveryHint` 为空，约束被迫打太极。**买家要的是"是/不是"，机器人给的是"我不知道"。**

**问题 B：目录 / 库存事实前后矛盾，缺乏稳定事实源**
- 代表用户消息：`全集共多少集？`、`包含 1-47全集嘛`
- 同商品（余红旧事全集）的两种回答：
  - 「具体集数商品详情里没标注，我这边也说不准，内容是全的完结版～」（回避）
  - 「是的，包含1-47集全集，4K高清版，还附小说剧本，网盘发货~」（自信断言）
  - 后续人工补：「34 集」
- 说明：机器人对同类问题的回答在"说不准"与"自信断言"之间摇摆，因为事实没有从单一可信源（商品规格表 / 在售清单）注入，而是依赖提示词里被截断的商品标题与描述 JSON。这是准确性的硬伤 —— 同一事实两种相反结论。

**问题 C：意图误分流导致偏题**
- 代表用户消息：`发网盘吗`
- 实际命中意图：`stock`（应为 `delivery`）
- 结果：即便该次恰好答出"对，度盘"，仍属于判定失准；一旦问题更复杂（"发夸克吗"），`stock` 意图缺乏发货话术，极易偏题或回避。
- 说明：`stock` 与 `delivery` 在口语里边界模糊（"发网盘吗"既问发货方式也问是否在售），当前组合词判定把它们切开，导致漏接管或错接管。

**问题 D：确认类 / 否定式是非题断言不稳**
- 代表用户消息：`我要夸克的`（在已答"包含1-47全集"后追问渠道）
- 机器人回答：「亲，具体网盘类型以商品详情和拍下后的发货消息为准哈，我这边先帮您确认下…」
- 说明：用户已明确表达诉求（"我要夸克的"），机器人仍未给出确定结论，反而继续回避。是非题 / 选择题意图缺乏"先给明确结论再补依据"的约束。

### 3.2 通用性类

**问题 E：意图正则覆盖不到口语问法**
- 漏接管的真实 / 探针问法：`百度吗`、`百度云的吗`、`百度网盘吗`、`网盘吗`、`度？`、`全剧吗`、`所有的吗`、`还有大班的吗`、`小鸡球球点读笔可以用吗`
- 规律：口语以"有没有 X / X 吗 / 支持 X 吗"为主，而 `ai_scope_config` 的 `delivery` 组合词只收录了书面问法"什么盘 / 网盘发货"，漏掉大量"X 吗"句式（与 2026-10-10 复盘 4.2 一致，仍未闭环）。

**问题 F：负向词与售前咨询死锁**
- 代表用户消息：`那能退吗？`、`退掉吧`、`我不买了`（售前咨询）
- 现状：`builtinComplaintPatterns` 把"退款|退货"列为负向词一票否决，售前"能退吗"也被当作售后纠纷拦掉，进不了 AI。
- 说明：应区分"咨询退款政策（售前，可 AI 答）"与"我要退款（售后，转人工）"。`compliance` 维度 14 条探针里，退款 / 发票 / 包邮类售前咨询目前无法稳定触达。

### 3.3 热点类

**问题 G：链接 / 提取码类高频诉求无自动应答**
- 代表用户消息：`这个链接能用多久`、`链接打不开了`、`之前发的那个链接失效了`、`提取码不对`
- 说明：`link-code` 维度 18 条探针为全体最高，是买家最高频的售后追问。当前机器人无"链接有效期 / 重发 / 提取码核对"的确定性应答能力，全部堆给人工。

**问题 H：履约类（付款未收到 / 重发）缺乏闭环**
- 代表用户消息：`我付款了但是没收到发货`、`再发一次链接吧`、`发货凭证在哪看`
- 说明：`fulfillment` 8 条、`order` 6 条探针指向"付款—发货—查收"闭环。机器人无法查询订单履约状态，只能转人工或回避。

### 3.4 性能类

**问题 I：人工排队长尾延迟**
- 依据：2026-10-10 复盘实测响应延迟中位数 42 秒、均值 943 秒，>10 分钟案例几乎全是人工介入；同一条百度网盘链接人工重复发送 46 次。
- 说明：AI 接管率低 → 确定性、可自动化的问题（渠道确认、链接重发）堆给人工 → 响应退化到小时级。这不是人的问题，是"AI 不敢接管 → 排队"的连锁效应。性能瓶颈的根因仍是准确性（I 可由 A/B/C 的修复间接消解）。

## 四、改进思路与依据映射表

> 优先级标尺：**准确性 > 通用性 > 热点 > 性能**。每条改进均锚定既有架构（三层配置 `ai_scope_config` / `ai_knowledge_config` / `ai_policy_config` + `aimatch` 组合词 + 评测 harness），避免割裂式重构。

| 编号 | 改进思路 | 优先级 | 对应问题 | 具体依据（用户消息 / 案例 / 数据） | 架构落点 |
|---|---|---|---|---|---|
| **M1** | **建立"商品 → 发货渠道"事实源，并注入 `inferDeliveryHints`** | 准确性 | A、C（部分） | 10/12 真实样本为渠道回避；`inferDeliveryHints` 恒空；标题含"双盘发货"但无具体盘名 | 扩展 `ai_live_context.go` 的线索来源，新增 `item_delivery_channel` 映射（可从历史已发交付消息反向抽取头部 SKU 渠道），经既有 `KnowledgeContext` 注入，不改三层配置契约 |
| **M2** | **统一商品事实源，消除目录 / 库存前后矛盾** | 准确性 | B、C | 同商品"说不准"vs"34集全集"矛盾；`stock` 误分流 | 让目录 / 规格 / 在售清单作为唯一事实源注入 `KnowledgeContext`；`stock` 与 `delivery` 共用商品事实，避免各算各的 |
| **M3** | **是非题 / 选择题意图加"先给明确结论"约束** | 准确性 | D | `我要夸克的` → 仍回避；`不是百度网盘吧`类二义 | 在 system prompt 追加确认义务（否定式按字面确认，不得只答"是的"）；属纯提示词约束，零代码改动，可经评测 harness 回归 |
| **M4** | **意图组合词从"穷举词表"转向"渠道词 + 疑问句式"** | 通用性 | E | `百度吗`/`网盘吗`/`度？`漏接管；口语"X 吗"句式 | 改 `ai_scope_config` 的 `delivery` 为"渠道词(百度\|度盘\|夸克\|网盘…) & 疑问句式(吗\|嘛\|有\|支持…)"；纯配置变更，即时生效 |
| **M5** | **解开"退款\|退货"负向词死锁，区分售前咨询与售后纠纷** | 通用性 | F | `那能退吗`/`退掉吧`被误杀；`compliance` 售前咨询不可达 | 负向词收窄为带动作主语（`我要退\|申请退款\|已退款`），纯咨询落 `refund` 意图走 FAQ；配置变更 |
| **M6** | **链接 / 提取码类高频诉求建确定性应答** | 热点 | G | `link-code` 18 条为最高频；链接失效 / 提取码不对 | 在 `ai_knowledge_config` 增加"链接有效期 / 重发 / 提取码核对"FAQ，并配置对应意图；复用三层语料机制 |
| **M7** | **履约闭环：可读订单履约状态并确定性应答** | 热点 | H | `fulfillment` 8 + `order` 6 探针；付款未收到 | 新增只读订单履约查询端口，注入"已发 / 待发 / 重发"话术；属能力扩展，沿用 capability 访问策略，不绕开权限判定 |
| **M8** | **提升 AI 接管率以消解人工排队长尾** | 性能 | I | 响应长尾均值 943s；同链接人工重复 46 次 | M1~M7 落地后 AI 接管率上升自然消解；并配合把"固定链接重复发送"等确定性动作自动化的既有方向 |

## 五、优先级排序与演进连续性

### 5.1 排序理由

严格按 **准确性 > 通用性 > 热点 > 性能**：

1. **准确性（M1/M2/M3）最先**：机器人"答错 / 答非所问 / 自相矛盾"直接摧毁买家信任，且是人工纠正信号的集中来源。M1（事实源）是贯穿全局的主根因，M2（目录矛盾）次之，M3（确认约束）成本最低、见效最快。
2. **通用性（M4/M5）其次**：意图正则与负向词是配置层问题，不碰代码即可提升接管覆盖面，ROI 高。
3. **热点（M6/M7）再次**：链接 / 履约是高频痛点，但属于"锦上添花"的能力扩展，应在事实源与意图判定稳定后再做。
4. **性能（M8）最后**：性能瓶颈是准确性的下游症状，不应单独为延迟做工程，而应由前序准确性修复自然消解。

### 5.2 与既有演进的连续性（避免割裂式重构）

本方案与三条既有主线保持同一演进脉络，不另起炉灶：

- **沿用三层可配置架构**：M1~M7 全部落在 `ai_scope_config`（边界/意图）、`ai_knowledge_config`（语料/FAQ）、`ai_policy_config`（策略）既有契约内，符合升级计划"低代码配置、改配置即时生效、不重启"的设计目标。新增事实源（`item_delivery_channel`）只是扩展 `inferDeliveryHints` 的线索来源，经既有 `KnowledgeContext` 注入，不破坏提示词拼接链路。
- **沿用 `aimatch` 组合词语法**：M4 的"渠道词 + 疑问句式"仍用既有的 `| & ! ( ) "..."` 语法表达，不引入新的匹配引擎。
- **沿用评测 harness 作门禁**：M3 的提示词约束、M4/M5 的组合词变更，均通过升级计划与评测机制方案定义的"决策层评测 + 内容层评测"卡口回归，防止写坏接管行为（负向词漏拦、意图错收）。真实样本库（12 条生产 + 48 条合成）即门禁的回归集。
- **与已落地的提示词修复互补**：`deliveryAnswerConstraint` 已改写为"有确定渠道必须直接回答"，本方案 M1 正是把"确定渠道"从"靠商品描述碰运气"升级为"靠事实源稳定供给"，两者叠加才完整闭环——这是对既有修复的延续与补全，而非推翻重做。
- **未纳入本次范围（避免范围蔓延）**：语义向量检索（Milvus）、槽位与多轮 SOP（换货/改地址/开票）、三级护栏等升级计划 §9 的"后续增强方向"，仍作为独立里程碑，不在本轮与事实源/意图修复混在一起，保持增量、可验证。

## 六、落地建议与门禁

1. **先补事实源（M1/M2），再调意图（M4/M5）**：事实源是其它改进的支点；没有事实源，意图接得再全也只能回避。
2. **以真实样本库为回归基线**：将 12 条生产事故样本 + 48 条合成探针固化为评测 harness 的回归集，任何 `ai_scope_config` / `ai_knowledge_config` / `ai_policy_config` 变更必须过决策层门禁（与评测机制方案一致）。
3. **M3 作为零代码快赢先行**：提示词确认约束改动小、风险低，可第一个合入并用评测 harness 验证。
4. **量化验收**：以"人工纠正信号命中率下降"和"发货/目录类确定性回答占比上升"为验收指标，而非仅看模型输出流畅度。
